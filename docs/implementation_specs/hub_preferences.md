# Hub localization and local preferences

## Responsibility and bootstrap

`src/hub/i18n.ts` owns the i18next/react-i18next instance, English source catalog, Korean catalog and semantic messages. `Hub.tsx` reads `HubPreferences` and initializes that language synchronously from embedded resources before rendering the shell. Missing preferences select English and Light independently of browser locale. Language changes update document language and visible labels without remounting Runner sessions. Both languages use the same layout and left-to-right direction.

Hub-owned UI, status, validation, tooltips and accessibility labels use semantic keys and named interpolation. Retained Hub messages store keys and values so a later language change also updates earlier errors and assignment evidence. Runner output, agent responses, user names, paths, commands and protocol values remain original. Uncoded native errors retain their raw diagnostic text; the Hub does not infer error identities from English prose. English is the runtime fallback for a missing translation, while automated catalog checks reject missing, unused or mismatched entries.

## Independent preference storage

`AppSettings.tsx`, opened from the toolbar, presents language and theme alongside installation management. The same controls remain available during mandatory installation setup. Changes retain the current selected Runner and live session objects. Installation startup and admission belong to [the installation gate](runner_terminals.md#installation-startup-gate), independently of preference persistence.

`preferences.ts` owns the versioned `agent-runner-hub.preferences.v1` local-storage document, language, theme, Single Entry choices, `confirmRunnerRemoval` and optional `runnerSelections` keyed by Hub tab UUID. Missing removal preferences default to enabled; App Settings exposes the confirmation checkbox in both languages and themes. The application uses the existing desktop WebView/browser origin's local storage. Requested selections are independent of Runner current, effective and next settings.

The store projects known nonsecret selection fields and writes atomic replacements after initialization or explicit edits. Missing choices remain empty until installation admission and authenticated options readiness. Malformed, unsupported and unreadable records remain untouched; this window disables preference writes. Concurrent record changes are retained rather than overwritten. A failed write retains the saved record and shows a translated warning while current window choices continue working.

`RunnerWorkspace.ts` and `RunnerLocation.tsx` retain their independent workspace and installation keys, validation, write and recovery contracts. The preference projection includes no authentication material, PTY identity, terminal contents, drafts, instruction bodies, reference state or uncertain execution outcomes.

## Single Entry boundary and reuse

`EntryDefaults` carries requested Target, complete model/reasoning/tier selection, exact account identity, Base Run Mode, explicit Direct Root and the always-new/reuse-idle allocation preference. `projectEntryDefaults` validates and copies only these nonsecret fields. Always-new is the default when the optional policy is absent; changing the toggle persists the explicit policy. Clearing a selection uses the allocated Runner's verified setting. Restored choices remain requests and are revalidated through that Runner's authenticated catalogs before submission.

`HubPreferences.update` remains the sole Hub preference writer. `RunnerSessions` composes `HubSelections` for Single Entry and each visible tab, supplying restored snapshots and narrow save callbacks. A tab with no saved choices copies existing Single Entry defaults; later edits and tab switches stay independent. Restarts display saved partial or unsupported values directly, without startup inspection or replacement. The optional initialized marker preserves a deliberately cleared selection. Catalogs, revisions, plans, receipts and work identity remain process-local; preferences never replay an assignment.

For never-initialized execution choices, `HubSelections` uses the existing spare or suitable ready session and `RunnerConfigService.inspect`. An allocation-policy edit alone does not initialize execution choices. It collects complete authenticated candidates, resolves the first account's own complete catalog, then chooses the first Target, account, Run Mode, model, reasoning and tier in returned order. It atomically saves untouched defaults together with newer allocation-policy and explicit Direct Root edits, without copying current/effective/next settings or inventing a Root. Fields deliberately selected or cleared during inspection survive; an account edit also excludes dependent model defaults. Restored partial execution selections remain authoritative. A changed inspection source cannot publish results or trigger automatic retries. Failed or unavailable initialization retains user edits with bounded feedback and an explicit refresh path. Restored catalogs load only for interaction or submission verification.

`runnerConfigDefaults.ts` maps verified registry identities and model combinations, including the full `agent_id/profile_name` pair. Legacy account-label fields remain readable but unresolved even if a current display label matches. Explicit exact-account selection replaces that legacy preference; no guessed migration occurs. On interactive inspection failure for a saved account, a bounded general inspection may expose verified replacement accounts while retaining the saved identity; model choices remain hidden until its account catalog matches. See [Runner session configuration](runner_session_config.md#preferences-and-single-entry-boundary) for catalog conversion and configuration receipts.

## Evidence destinations

- `tools/i18n/check.mjs` and `tests/i18n/catalog.test.mjs`: locale parity, named variables, source arguments, unused keys, untranslated JSX and negative validation cases; `npm run test:i18n`.
- `tests/e2e/preferences.spec.mjs`: first-render language, both themes and languages, accessible layout, new-page restoration, malformed/unreadable data, write failures and concurrent-record retention through the installed browser fixture. `tests/e2e/hub-selections.spec.mjs` exercises ordered initialization, destination catalogs, partial restoration, delayed edits and failed inspection; `hub-selection-ui.mjs`, registered in `runners.spec.mjs`, exercises automatic startup, tab inheritance and independent restart restoration through simulated native responses.
- `tests/e2e/runners.spec.mjs`: current Runner observations remain separate from defaults; user-selected defaults survive reload and are revalidated; live language/theme updates preserve terminal, process, control, image and reference ownership through the simulated native transport.
- Existing native Rust and platform build paths remain unchanged. Browser simulations, native compilation/tests, packaged WebView persistence and actual manual acceptance are separate evidence levels.
