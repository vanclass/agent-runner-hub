# Hub localization and local preferences

## Responsibility and bootstrap

`src/hub/i18n.ts` owns the i18next/react-i18next instance, English source catalog, Korean catalog and semantic messages. `Hub.tsx` reads `HubPreferences` and initializes that language synchronously from embedded resources before rendering the shell. Missing preferences select English and Light independently of browser locale. Language changes update document language and visible labels without remounting Runner sessions. Both languages use the same layout and left-to-right direction.

Hub-owned UI, status, validation, tooltips and accessibility labels use semantic keys and named interpolation. Retained Hub messages store keys and values so a later language change also updates earlier errors and assignment evidence. Runner output, agent responses, user names, paths, commands and protocol values remain original. Uncoded native errors retain their raw diagnostic text; the Hub does not infer error identities from English prose. English is the runtime fallback for a missing translation, while automated catalog checks reject missing, unused or mismatched entries.

## Independent preference storage

`AppSettings.tsx`, opened from the toolbar, presents language and theme alongside installation management. The same controls remain available during mandatory installation setup. Changes retain the current selected Runner and live session objects. Installation startup and admission belong to [the installation gate](runner_terminals.md#installation-startup-gate), independently of preference persistence.

`preferences.ts` owns the versioned `agent-runner-hub.preferences.v1` local-storage document, language, theme, Single Entry choices, `confirmRunnerRemoval` and optional `runnerSelections` keyed by Hub tab UUID. Missing removal preferences default to enabled; App Settings exposes the confirmation checkbox in both languages and themes. The application uses the existing desktop WebView/browser origin's local storage. Requested selections are independent of Runner current, effective and next settings.

The store projects known nonsecret selection fields and writes atomic replacements after initialization or explicit edits. Missing choices remain empty until installation admission and authenticated options readiness. Malformed, unsupported and unreadable records remain untouched; this window disables preference writes. Concurrent record changes are retained rather than overwritten. A failed write retains the saved record and shows a translated warning while current window choices continue working.

The optional `shortcuts` projection stores an additional Single Entry assignment chord, Single Entry navigation and a Runner-number modifier family in the same record. Loading accepts current maps directly; unsupported optional fields use current defaults while independently valid custom fields and other preferences remain usable. Retired Ctrl+Enter assignment and Home navigation have no conversion rules. Restoration never writes storage. `shortcuts.ts` validates the complete map for explicit saves. Enter submission, Shift+Enter newline, IssueRun Ctrl+Enter and Ctrl+Home/End/PageUp/PageDown remain reserved Hub behavior. The `ShortcutSettings.tsx` dialog, opened through App Settings, captures a draft, rejects overlaps and reserved combinations, and applies the map together. Persistence failures retain the dialog and warning; local choices never imply a successful save. Only one modal is mounted at a time; closing shortcuts returns to App Settings and its shortcuts trigger. Focus, Tab and Escape remain managed by each dialog. See [Hub keyboard navigation](runner_terminals.md#hub-keyboard-navigation).

App Settings also stores the optional unified/by-mode `domainDisplay` choice. Its history, tab affinity and display-order ownership are separate from requested execution settings: see [Runner navigation presentation](runner_navigation.md). Absent v1 values select unified display; malformed values retain the original preference record under the same protection boundary.

`RunnerWorkspace.ts` and `RunnerLocation.tsx` retain their independent workspace and installation keys, validation, write and recovery contracts. The preference projection includes no authentication material, PTY identity, terminal contents, drafts, instruction bodies, reference state or uncertain execution outcomes.

## Single Entry boundary and reuse

`EntryDefaults` carries requested Target, complete model/reasoning/tier selection, exact account identity, Run Mode, explicit Direct Root and allocation policy. `projectEntryDefaults` validates and copies only these nonsecret fields. The App Settings dropdown offers always-new (the absent-policy default), reuse-same-mode and unrestricted reuse-idle. Existing saved policies retain their behavior. It uses the Single Entry selection writer and assignment edit lock. An empty account displays Select an account / 계정 선택 and cannot submit configured work; it never adopts a destination account implicitly. Restored choices remain requests and are revalidated through the destination's authenticated catalogs before submission.

`HubPreferences.update` remains the sole Hub preference writer. `RunnerSessions` composes `HubSelections` for Single Entry and each visible tab, supplying restored snapshots and narrow save callbacks. A tab with no saved choices copies existing Single Entry defaults; later edits and tab switches stay independent. Restarts display saved partial or unsupported values directly while automatically loading authenticated options without replacing saved requests. The optional initialized marker preserves a deliberately cleared selection. Catalogs, revisions, plans, receipts and work identity remain process-local; preferences never replay an assignment.

After verified installation admission and authenticated service readiness, `HubSelections` attempts catalog loading for both fresh and restored choices through the existing spare or suitable session and `RunnerConfigService.inspect`. An unchanged failed source is not retried by polls, renders or focus. Source replacement or an observed loss and recovery of authenticated inspection readiness permits another attempt; account edits retain the existing account-dependent inspection path. Only never-initialized execution choices adopt verified current defaults through `configToEntryDefaults` with fresh same-source observation. New choices use Task Run; saved partial, unsupported and deliberately cleared values remain authoritative. In-flight edits survive, and an account edit excludes dependent model defaults and prevents publication of the old account catalog. Allocation policy alone does not initialize execution choices. Initialization saves through the existing projection without inventing Root or copying effective/next settings. Superseded sources cannot publish results. Failed inspection retains edits and diagnostic feedback. The selection UI has no refresh button or normal-startup control-channel warning; destination submission still verifies fresh authenticated configuration.

`runnerConfigDefaults.ts` maps verified registry identities and model combinations, including the full `agent_id/profile_name` pair. Saved account-label fields are inert and excluded from active selections and conversion, even when a present-day display label matches. Dropping a historical account label retains initialized intent in memory even when allocation policy or Root survives, preventing automatic account initialization or an eager write. Allocation-policy-only records without historical execution selections remain eligible for initialization. Independent current selections and explicit initialized markers survive. On interactive inspection failure for a saved exact account, a bounded general inspection may expose verified replacement accounts while retaining the saved identity; model choices remain hidden until its account catalog matches. See [Runner session configuration](runner_session_config.md#preferences-and-single-entry-boundary) for catalog conversion and configuration receipts.

- `tests/e2e/wg2-loading.spec.mjs` covers delayed authenticated readiness and failed automatic inspection for fresh/restored choices. `tests/e2e/wg2.mjs`, registered by `runners.spec.mjs`, covers three-policy allocation with mixed/busy/missing candidates, display independence, localized Light/Black settings, restart persistence, account rejection and assignment locks through synthetic native responses.

- `tests/e2e/preferences.spec.mjs`: first-render language, both themes and languages, accessible layout, new-page restoration, malformed/unreadable data, write failures and concurrent-record retention through the installed browser fixture. `tests/e2e/hub-selections.spec.mjs` and `hub-selection-initialization.spec.mjs` exercise current-account initialization, fresh observation requirements, Task Run defaults, partial restoration, delayed edits and failed inspection; `hub-selection-ui.mjs`, registered in `runners.spec.mjs`, exercises automatic startup, App Settings reuse edits, tab inheritance and independent restart restoration through simulated native responses.
- `tests/e2e/runners.spec.mjs`: current Runner observations remain separate from defaults; user-selected defaults survive reload and are revalidated; live language/theme updates preserve terminal, process, control, image and reference ownership through the simulated native transport.
- Existing native Rust and platform build paths remain unchanged. Browser simulations, native compilation/tests, packaged WebView persistence and actual manual acceptance are separate evidence levels.
