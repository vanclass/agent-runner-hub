# Runner session configuration

## Responsibility and entry points

`src-tauri/src/desktop_terminal/features.rs` registers the implemented native feature surface, while `session_config.rs` owns typed session configuration requests and sanitized responses. The existing `control.rs` owns authentication, exact wire identity, monotonic request IDs, FIFO correlation and completion. `control_windows.rs` continues to own private pipes and its nonblocking worker. `runner_feature` uses the existing Tauri window/session ownership check and returns native admission without waiting for a remote owner while holding a session mutex.

`RunnerControl` composes one `RunnerConfigService` per Runner session and feeds it native snapshots. The service owns drafts, verified catalogs, plans, request completion, application receipts and post-apply observations. `HubActivity` derives concise presentation from that service and `HubSelections`. The current Runner API contract is AgentRunner's `SESSION_CONFIG.md`; Hub does not implement settings owners, consent or configuration-file writers.

Native capability discovery follows an authenticated completed observation. Only locally implemented feature/version/operation combinations are exposed. A native instance generation, together with the owning PTY session, fences frontend results without exposing process/session/connection wire identities or the private key. An unbound startup snapshot cannot establish that identity. Exited instances reject late publication; changing the selected tab never retargets a request.

`RunnerConfigService.inspectionUnsupported` distinguishes a ready authenticated snapshot without supported inspection from capability discovery still in progress. `HubSelections` stays neutral before that evidence, shows option-loading activity only during inspection, and removes obsolete unsupported guidance when the source disappears or its evidence changes. Genuine inspection failures and explicit selection requirements remain visible. Confirmed unsupported inspection retains its localized guidance and configuration restrictions; no timer or persistent event log participates in this decision.

## Requests, completion and bounded waiting

The typed feature wrapper selects `session_config` and an inspect, plan or apply request. Native adds the unchanged v1 authentication/identity envelope. Inspect can carry an account pair, offset and options guard. Plan carries desired settings. Apply carries the exact desired/revision/plan_id returned by a ready plan. Options evidence is inspect-only.

Explicit request kinds separate observe, command, reference, image and feature completions. Configuration results cannot become observations or change observation freshness. Admission distinguishes local validation/encoding failure, submission with unconfirmed Runner admission, queued admission and pre-admission rejection. Only a matching completed result supplies owner evidence. Pending interaction remains Runner-terminal-owned; Hub structured replies are deferred and no direct terminal fallback or generated confirmation is permitted.

The native worker continues reading and writing while remote owners work. Each Runner has its own worker, and frontend waits consume snapshots rather than blocking the worker or a shared mutex. Same-session requests retain Runner FIFO ordering. Queued does not establish configuration processing or work start; canonical work start evidence belongs to the separate work feature.

Completion deadlines are request-specific and apply to the FIFO head. Followers receive their own waiting interval when the preceding request settles, so an ordinary reference/image/observe cannot expire solely because a valid configuration request is ahead of it. The bounded limits are owned in `session_config.rs`; they account for Runner's paged model RPCs, policy checks and repeated apply validation. Existing terminal-owned pending interaction remains exempt from the normal completion deadline. A separate bounded frontend delivery grace classifies missing receipts without replay.

Native tracks frame byte positions: an untouched outgoing feature frame is provably not sent; partial/full transmission without a definitive response remains unknown. EOF, timeout and connection loss preserve that distinction and all already-completed receipts. No uncertain apply is automatically repeated, reassigned or inferred successful from coincidentally equal current values.

## Explicit Test Runner acceptance

`session_config.inspect` accepts a read-only request with `execution_context: "test"` and an explicit `agent_id`. The authenticated capability must advertise both `test_account_selection` and the requested ID in `test_account_providers`. This request has no account or pagination fields. The reply must identify the requested Provider and its exact configured test profile. The native adapter checks `codex_home` for Codex or `claude_config_dir` for Claude against the canonical `local/profiles/<agent_id>/accounts/<profile_name>` directory under the opened installation. It rejects aliases, traversal, missing paths, unavailable authentication and unrelated installations. The authenticated transport binds the response to the existing wire session.

`RunnerConfigService.selectTestAccount(provider)` returns the qualified account and its location evidence for the exact PTY/session generation and installation. Discovery leaves drafts, preferences, current settings and work untouched. Failures retain the Runner diagnostic and direct the operator to **Settings > Test settings** in that installation.

The explicit native work-acceptance caller is `work_acceptance.rs::public_work_identity_receipts_status_and_exact_owned_shutdown`. Its owned first session uses `session_config_acceptance.rs::configure_test_session`: test selection, destination-account catalog, ordinary plan/apply, completed committed receipts, fresh effective identity and unchanged test home/root must precede its single submission. The second independent session remains untouched. These acceptance-only consumers introduce no ordinary-tab account mode or saved preference. Installed discovery exercises read-only test selection separately; a missing authenticated profile blocks model acceptance before submission. Fixture and transport success never establish genuine image delivery.

## Verified candidate catalogs

`runnerConfigContract.ts` validates the typed projections and page invariants. Each collection starts at offset zero and captures native instance identity, requested account, returned catalog account, revision, options_revision and totals. Guarded continuation sends the first options token unchanged and requires the exact next offset, expected page lengths/progress, stable Run Modes, matching evidence/totals/account and unique stable candidate identities.

Candidates remain private until the entire collection passes pagination and identity checks. Hub takes the effective Provider from authenticated `selection.agent_id` and reconciles it with Session Configuration. Accounts must match that Provider, and models must come from the exact catalog account. `none` or missing Provider evidence leaves both lists empty. An authoritative unavailable model catalog can still supply independent Target and Run Mode choices. Changing accounts invalidates the plan and requires the destination account's catalog.

An effective Provider transition invalidates the previous actual settings, options revision, catalog and pending plan in that session. In-flight reads and plans can complete for receipt tracking, but their data cannot become current after the transition, including when the session returns to the original Provider. Apply receipts retain their exact request identity. A fresh observation of the current Provider is required before Hub submits configured work after attachment preflight.

Single Entry and Runner-tab settings display the configured startup Provider from authenticated `observation.configured_startup_agent_id` alongside the effective session Provider. The startup display follows fresh observations and distinguishes Codex, Claude, and None. Missing, null, and unsupported evidence displays Unavailable. A retained session can have a different effective Provider. The startup setting is display-only in Hub and has no role in catalog selection, session bindings, or workload authority.

A new Runner can return a complete catalog while its current Target is unbound. `HubSelections` retains those verified candidates for explicit settings selection without guessing a Target or saving incomplete current defaults. Catalog availability and complete default initialization are separate; the shared plan/apply and work-admission gates still apply.

Native and frontend admission require options_revision capability support and a valid options digest on every inspection page, including a complete single page. Incomplete/unverifiable selections remain disabled. Missing or unsupported session configuration does not disable supported authenticated commands, references or images; terminal logs remain read-only.

## Draft, plan and apply

Actual configured settings, effective execution settings, next execution settings, the user's draft and saved Hub defaults remain separate. IDs come from candidate records, including the full agent_id/profile_name account pair. Unlisted values remain visible and are never replaced automatically. Model/reasoning/tier combinations must match the destination catalog; Root is explicit input and Runner performs its actual filesystem/policy checks.

Direct/Pure Direct Root supports typing, paste and the shared [native directory picker](runner_terminals.md#single-entry-assignment). Hub controls change only requested local selections; initialization and editing never plan, apply or submit work. A missing stored Direct Root requires explicit input before configuration planning/submission. Draft replacement, tab unmount, competing operations and native session end invalidate an outstanding picker result. Both submission entry points use `runnerSubmission.ts` to verify requested selections against fresh destination options, plan and apply necessary changes, then verify before work admission. The right panel has no manual Plan or Apply action.

Planning changes nothing. Invalid plans, required confirmations and unsafe configuration block work submission. The read-only panel shows differences, receipts and original diagnostics. Context release or Brief discard retains Runner's canonical owner semantics; [structured Hub replies are deferred](runner_terminals.md#structured-foreground-interactions), and canonical foreground owners remain blocked. Hub supplies no private confirmation logic. Draft edits and new inspection invalidate a plan. Immediately before necessary Apply, the service reinspects and rejects a changed revision; Runner repeats its own authority/applicability checks. A ready no-op plan reuses the complete inspection when its canonical revision matches; a different revision requires reinspection, without a mutating request.

Completed per-setting outcomes retain success, rejection, cancellation, failure, unknown and not-attempted independently. Success requires an owner acknowledgement and a matching committed projection; ordered stops and aggregate status are validated. Earlier success survives partial failure and a failed final inspect. Inspection proves current state, not causation for an unknown request. A delayed authoritative receipt can resolve a delivery timeout only for its exact request in the same live native instance; final observation remains separate.

## Preferences and Single Entry boundary

`runnerConfigDefaults.ts` maps target registry identities, exact agent/account pairs, model IDs/reasoning/tier, canonical Run Mode and Direct Root through verified complete candidates. TaskRun submission excludes Target and model/reasoning/tier from this configuration projection: its leading instruction metadata and Runner session fallback own those decisions. Stored account labels are excluded from active defaults and conversion; matching display names grant no identity or execution authority. Shared configured submission requires an explicit exact account pair, including for partial restored selections. The reverse safe projection requires verified candidates and current observation evidence. No guessed storage migration is introduced.

Hub refreshes session-derived account and model choices against the new Provider and restores explicit preferences for that Provider. Legacy unqualified selections remain unresolved until the user replaces or clears them. Single Entry skips reuse or promotion candidates whose observed Provider differs from the requested account, and a tab submission binds to its existing session. Both verify the destination's account and model catalog and retain existing Runner work authority. Work admission and start have separate receipts. See [Hub preferences](hub_preferences.md#single-entry-boundary-and-reuse) and [instruction submission](runner_terminals.md#single-entry-assignment).

On hidden-idle promotion, the service retains all applications, receipts, actual settings and uncertainty for admission and reconciliation. Its presentation boundary excludes prior applications and diagnostics from the new tab; later configuration operations display normally. The lifetime and work/image counterparts are described under [tab status and closing](runner_terminals.md#tab-status-and-closing).

## UI and evidence destinations

`TaskPanel.tsx` composes shared Hub selection controls for Single Entry or the selected tab. It owns only panel collapse and responsive presentation. Selection initialization, persistence and independent tab restoration belong to [Hub preferences](hub_preferences.md#single-entry-boundary-and-reuse); Runner services retain actual/effective/next settings and plans/receipts internally. The panel scrolls independently and uses a collapsible narrow-window overlay. Detailed settings, plans, receipts, diagnostics and JSON disclosures are absent.

`Workspace` attaches one fixed, non-wrapping `HubActivity` status footer immediately below the composer. Its complete localized Hub sentence shares the composer's responsive horizontal inset and uses one consistent text style, including verified application text such as `Hub 설정 적용을 확인했습니다.`. Idle leaves its reserved line empty. Single Entry supplies only its existing selection activity; a Runner supplies its own selections and configuration service. The footer adds no store, polling, persistence, history or interaction controls. It excludes PTY, agent and work-result activity; detailed diagnostics remain with their state owners and Hub logging.

Active configuration request states and operations take precedence over option loading, then plan refusal/confirmation, the latest application, selection guidance/errors and configuration failures in the service's current presentation boundary. Each renders one localized message, merging overlapping selection/configuration inspection. Queued admission is pending, never successful application. Confirmed not-sent, rejection, failure, unknown outcome, partial commits and unavailable final inspection remain distinct; success requires an authoritative applied receipt and verified inspection. Partial takes precedence over unavailable inspection when both are true. The stable polite status region changes only when its concise content changes. Retained request receipts preserve plan refusal/confirmation across automatic catalog inspection that clears the transient plan; promotion advances the existing service presentation baseline without deleting internal evidence.

`HubSelectionSettings` presents Account first, then a Run Mode dropdown, its conditional destination, and Model Settings with Model, Reasoning and Fast. `runModeLabel.ts` supplies display-only names: Pure Direct Run, Direct Run, Task Run and Issue Run; persisted and submitted mode IDs remain unchanged. Task/Issue show the target selector with registered project names as labels, retaining exact owner/project values. Direct/Pure Direct show only Root in that position. Hidden target and Root requests survive mode changes; Root is ignored for other modes. Account is always exposed without Advanced Settings. Reuse belongs to App Settings through the existing Single Entry selection writer. Both contexts use `HubSelections.setDefault`. Fast maps to the existing `default`/`fast` tier contract and is disabled when the authenticated model lacks either choice. There is no separate default-tier button; unchecking Fast on a supported model selects `default` while preserving the model and unrelated fields. Unsupported values remain visible and are not automatically changed. Saved model members survive account/model changes and incompatible values require explicit resolution. Current/effective/next settings remain separate from requested selections.

The English/Korean catalogs cover selectors, concise activity, errors and accessibility. Activity exposes no request/event IDs, raw diagnostic codes or setting dumps. The panel and footer use existing Light/Black variables. Command shortcuts and manual configuration controls are absent from the right panel. Toolbar App Settings retains installation, language and theme management and opens the keyboard-shortcut dialog, which follows [Hub preferences](hub_preferences.md#independent-preference-storage) and [Hub navigation](runner_terminals.md#hub-keyboard-navigation).
