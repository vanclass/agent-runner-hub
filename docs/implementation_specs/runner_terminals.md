# Runner terminal ownership

## Session lifetime and identity

`src/hub/RunnerSessions.ts` owns each Runner's terminal, PTY connection, input ordering, output parser, scrollback, draft, and observed process state. `Hub.tsx` owns selection and composes the views. A keyed `Workspace.tsx` can unmount: `RunnerTerminal.tsx` only detaches its geometry observer. Selecting the tab reattaches the same xterm element and fits that existing terminal. Inactive terminals continue parsing and acknowledging output; selection never launches or closes a process.

Names are local display labels. The row identity and its current native PTY identity remain stable when renamed. Rows retain creation order, and Single Entry remains above their independently scrolling list. Tab metadata survives reopening through the Hub-owned workspace boundary below; terminal buffers, drafts and execution attempts remain process-local.

Composer drafts and pending submission belong to the session snapshot. Switching views during a pending PTY write preserves its disabled/busy state and cannot submit the same draft again; successful delivery clears that session's draft.

## Durable workspace and recovery

`RunnerWorkspace.ts` owns the versioned `agent-runner-hub.workspace.v1` local-storage record and its explicit metadata projection. `RunnerSessions.ts` restores the validated records in saved creation order before launching any processes. The manifest retains stable Hub IDs, labels, order, verified installation roots, launch intent and separate last-authenticated and historical target/run-mode/workflow contexts. A single atomic replacement commits relevant changes during use; failed writes retain the prior commit and display a warning. Unsupported or unreadable manifests remain untouched. Invalid or duplicate records are skipped independently with a visible diagnostic.

The optional `recoveryHint` retains the earlier process context while historical recovery remains unconfirmed; `lastVerified` continues following fresh authenticated observations. On load, existing version-1 records without a hint promote their saved `lastVerified` before any fresh process starts. An existing hint always survives later observations, setting changes and reopening. Both contexts use the same explicit nonsecret projection; neither provides current settings or recovery authority. Current settings come only from the current control snapshot.

Previously running or still-starting tabs invoke the existing native Runner launch path once each. Installation resolution and managed-runtime verification happen again before process creation. A missing installation or failed launch remains in its own tab for the next reopening; ended tabs remain visible without starting a process. Native PTY/control identities are newly allocated and never loaded from storage. Tab switching retains the new session mapping. Window teardown preserves the committed launch intent while the native owner settles all descendants.

`RunnerRecovery.tsx` distinguishes a restored workspace and fresh process from unconfirmed historical work. It labels the retained target, binding, run mode and workflow as previous-process information, separately from current settings, and offers `/recover` only from a fresh canonical visible/enabled command projection. Runner owns candidate discovery, selection, admission, confirmation and continuation in that tab's terminal. Rejection, pending interaction, unavailable recovery and command completion remain distinct; accepting a command alone does not establish successful TaskRun, DirectRun or IssueRun recovery or retire the historical hint.

The current public control projection provides no logical Task/Issue/workload identifier or authoritative work-recovery receipt. Hub invents none and does not persist the private transport session identity. The manifest excludes PIDs, handles, control keys/capabilities, credentials, terminal output, composer input, Single Entry submissions and uncertain commands. Restoration never reconnects to old processes or replays instructions, selections or commands. Scheduling and automatic work recovery remain outside this integration.

## Single Entry assignment

`singleEntry.ts` owns the process-local source draft, active requested defaults and assignment result; `SingleEntryComposer.tsx` renders that state. User-selected defaults are persisted separately through [Hub preferences](hub_preferences.md) and revalidated before sending. The existing `RunnerSessions` registry supplies sessions in creation order and the owned launch path. Each `RunnerSession` reserves its own input for the exact submission before configuration or PTY work. View changes do not release the reservation or reset the source draft.

Eligibility requires a running owned session, negotiated input protocol, empty Hub composer, untouched terminal input, fresh authenticated `INTERACTIVE_READY` observation, no execution/workflow, attention, suspension or unsettled control result. Observed enabled `/target` is the Runner-owned released Task/Issue authority evidence; enabled `/files` additionally excludes competing recovery and auto-resume. Missing evidence excludes a candidate. Native observation serial/age metadata advances only on completed authenticated observe responses. After reserving the first eligible session, assignment waits for a newer observation and rechecks readiness. If none qualifies, it reserves a newly created session before starting it and waits for verified readiness. A selected session that loses eligibility leaves an incomplete assignment without reassignment.

Default choices come only from fresh observed effective values, with a choice to retain the selected Runner's verified settings. The requested target, account, run mode and complete model selection are compared with that Runner's observations; effective and next model selections must agree. Changing defaults does not mutate any Runner. The current contract offers terminal-owned settings menus without a value catalog or automatic mutation API. A mismatch holds the instruction unsent and exposes the selected Runner's menus. The user can release the known-unsent assignment while retaining its draft or explicitly move it into that Runner's composer. Cancellation/rejection never constitutes settings confirmation.

After verification, one protocol submission is written through the existing PTY bridge. Successful delivery clears the source draft and releases its reservation; this confirms PTY delivery, not Runner acceptance or completed execution. The session remains excluded from automatic reuse because the protocol has no instruction receipt or editor-empty proof. Any prior manual terminal input likewise prevents automatic reuse. Failed/ambiguous writes retain the source draft and reservation and block retry/reassignment. There is no persistent queue, scheduler, concurrency cap, restored assignment or second Runner lifecycle authority.

## Native launch and shutdown

`src-tauri/src/desktop_terminal/runner.rs` accepts an installed workspace or its `agent_runner` folder. It verifies that the managed Python environment imports that installation's exact Runner source. Windows launch resolves the underlying interpreter and supplies the managed venv launcher context, avoiding an extra venv redirector PID while retaining the same environment. It runs the public `-I -m runner run --repo-root <workspace>` entry with the retained backend. Shell aliases are not executables. Invocation-scoped Runner coordination variables and Python path overrides are removed from the launch environment. Runner source, environments, credentials and runtime data stay in the configured installation.

On Windows, verification still uses the canonical filesystem identity, while returned DOS/UNC installation paths use ordinary external argument spelling. This prevents verbatim canonicalization prefixes from creating a mismatch with paths reported by Runner's App Server. Other device path kinds retain their original spelling.

The existing Desktop Terminal bridge and native `Sessions` registry remain the PTY backend. Windows Runner sessions use a separate non-inheritable Job Object with kill-on-close and no breakaway permission. The vendored portable-pty extension composes JOB_LIST, HANDLE_LIST and ConPTY startup attributes. Assignment occurs before Python executes; assigning an already running child would leave a descendant-creation race. Only the two dedicated child control endpoints are inherited. Parent endpoints and the Job Object remain non-inheritable; redundant child endpoints close immediately after creation. The Hub remains outside those per-Runner jobs.

Explicit termination, natural root exit, native window destruction, and final native ownership cleanup settle the owned job. Job termination waits for its active process count to reach zero. Natural exit is published after residual descendant cleanup and terminal output drainage. Unrelated PTY sessions and unrelated processes are outside that job. The generic Desktop Terminal request retains its original direct-child behavior.

macOS installation resolution is implemented, but Runner launch is gated before Runner process creation: initial POSIX process groups cannot contain children that start another session. Per-user launchd service removal does not establish detached-descendant ownership. Darwin's recursive kqueue tracking flags are unsupported; per-process exit observation does not create inherited membership. No supported containment mechanism is selected for production. Installed-Runner and native-window acceptance remain separate from compilation and process-fixture evidence.

The vendored Unix cloned killer sends SIGHUP to the direct child PID. Neither this operation nor killing the initial process group establishes detached-descendant containment. The existing Runner's POSIX group cleanup and cooperative shutdown are insufficient evidence to remove the macOS launch gate; a matching native detached-descendant fixture and installed-Runner acceptance remain required. A launchd job's process-group cleanup must not be treated as equivalent to a Windows Job Object.

`tests/native/macos_containment.py` executes bounded native fork/session and launchd experiments through the existing desktop CI on both macOS architectures. `macos_kqueue_probe.c` separately compiles and executes API registration receipts and fork-event observations. The fixture uses a private Unix-socket roster and per-process exit events as independent ground truth; candidates receive only their original PGID or unique service target. This cooperative roster is a fixture oracle, never a proposed production ownership mechanism.

Every fixture participant has an independent absolute wall-clock expiry, including orphans and processes that ignore termination signals or close standard streams. Calibration omits candidate cleanup and observes that expiry. Separate control channels clean up failed candidates, and only exact ephemeral launchd services are removed. CI retains host/manual details, operation results, per-process observations and final absence evidence even on failure. It does not copy or require a private Runner installation.

## Native executable build entry

`tools/hub-native.mjs` composes the installed Tauri host preparation, checkout build lease, backend staging and desktop feature selection. Its explicit absolute Cargo target directory allows Windows callers to select a short real output/cache path while frontend and backend staging remain checkout-local. It does not change managed build tooling, Runner installations, original Cargo locks or previous frontend output. `--help` describes build and native test commands; Cargo owns the selected output cache.

The standalone build passes a relative frontend directory to Tauri so Windows drive letters cannot be interpreted as URL schemes. The ordinary Tauri CLI enables production asset serving even for this debug executable; no test runtime branch or additional Cargo feature is used. The standalone build is distinct from Build System packaging and native development. A successful build establishes compilation and executable availability; GUI interaction, process cleanup and installer acceptance require their own observations. Build System remains the packaged-product owner.

## Input and process observations

`runnerInput.ts` honors the Win32 input mode requested through ConPTY. Physical keys retain their virtual key and modifiers; the composer encodes Unicode as UTF-16 key records and embedded line breaks as Shift+Enter, followed by one ordinary Enter. On standard VT terminals, the composer uses the negotiated bracketed-paste protocol and a separate Enter. Terminal responses and binary input retain their protocol bytes. The composer appends to any existing terminal draft; it does not replace Runner's own editor or interpret commands.

The UI reports starting, successful process launch, launch failure, and observed exit/code or transport errors. Terminal text never establishes task readiness, work completion, or assignment state. Launch and unexpected-exit failures affect only that session. Single Entry assignment uses the authenticated evidence above; workspace restoration never restores its pending assignments. xterm query replies and focus notifications retain their protocol path without becoming user-draft evidence; ordinary terminal typing still excludes automatic assignment.

## Local control and reference boundaries

`desktop_terminal/control.rs` owns the native v1 protocol and allowlisted public snapshots; `control_windows.rs` owns anonymous pipes, secure random launch identity/key, bounded I/O and worker cleanup. The hello must match the created child PID and expected fresh session, and an authenticated observation must complete before commands become available. Keys and raw wire identities remain native-only. Each existing session owns one client until exact process exit, termination or Hub closure, independent of selected tabs.

Controlled Windows launches use explicit NULL standard-handle slots with `STARTF_USESTDHANDLES`, allowing ConPTY to initialize console streams while excluding Hub stdio from inheritance. The compatible installed Runner public entry acquires its implementation generation and retains interactive ownership in the exact created process for controlled launches. Ordinary launches retain Runner's restart supervisor; controlled launches canonically disable `/restart`. Hub uses the public entry without bypassing generation ownership, weakening PID verification or replaying uncertain commands.

Runner owns canonical settings, command availability and foreground coordination. Native observations refresh those projections without parsing terminal text. Queued admission, pending terminal interaction, accepted/rejected completion, failure and uncertain outcomes remain separate. Only completed responses can supply owner status and allowlisted change acknowledgements; a completed command's canonical observation updates the existing snapshot immediately. Terminal cancellation retains Runner's rejected/CANCELLED outcome. The PTY exit event includes the final allowlisted native snapshot so a completed result is not lost between frontend polls. Disconnects preserve uncertainty for requests without authoritative completion; commands are never replayed automatically. A pending foreground interaction does not time out while awaiting terminal answers.

`runnerControl.ts` owns the frontend snapshot reader and process-local shortcut preferences. `RunnerControls.tsx` shows effective settings and next configured differences, opens complete observed slash submissions and presents disabled reasons and completed change acknowledgements. Menu captions and empty child syntax stay inside their terminal-owned parent flow. Local visibility/order changes do not mutate Runner preferences. Terminal typing and composer input retain the existing PTY path and Runner's input authority. The connected workspace scrolls while retaining usable terminal space for foreground menus.

`referenceSelection.ts` owns process-local attachment candidates, previews and correlation with native registration/removal receipts; `RunnerReferences.tsx` presents each candidate separately from Runner's registered inventory. Pickers and selected-window drops keep their original session owner and existing immediate path-registration behavior. Explicit Clipboard image actions create independent staged candidates, including duplicate-looking images, without registration until ordinary composer submission. Each live candidate can be cancelled individually. Clearing registration history removes only submitted, cancelled or removed display records; live attachments and uncertain attempts remain visible.

`desktop_terminal/references.rs` validates the allowlisted reference extension and metadata. Capability discovery uses only a completed authenticated observation; the exact v1 hello remains unchanged. Registration shares the existing pipe, private identity and monotonically increasing request sequence with observe/command. Only completed `registration_status: registered` with a valid stable reference ID becomes registered. Native admission failure, queued admission, foreground interaction, rejection, failure and unknown outcome remain distinct. Image-detail selection and cancellation use the existing Runner terminal. Unknown attempts are retained and never automatically repeated or matched by name, path or terminal text.

Inventory reconciliation reads all `references.list` pages twice and requires matching complete ordered samples, consistent totals, advancing offsets and unique stable IDs. Changing, incomplete or oversized samples block submission. These are conservative samples, not a transactional Runner snapshot. Display indexes and names never identify a removal. The optional authenticated `reference_removal` capability enables `references.remove` by the exact committed ID; only its completed matching receipt confirms removal. Pending or unknown removal blocks ordinary submission until the owning Runner authoritatively confirms absence. Older capable Runners require `/files` removal and reconciliation. No receipt or inventory sample releases source bytes.

Ordinary `RunnerComposer` instructions pass through one per-session attachment preflight in `RunnerSession.submit`. It locks the exact draft and selection, serializes surviving staged registrations in selection order, waits for completed receipts, and verifies intended IDs and the absence of cancelled IDs against the stable final pending set. Other pending references remain intact and require explicit review before inclusion. A rejected, failed, cancelled or uncertain attempt stops delivery with the draft and receipts retained. The existing PTY path receives the instruction once after verification; an uncertain write is never automatically replayed. Terminal answers remain available for Runner-owned image-detail/cancellation interactions. Slash commands, terminal-owned input and Single Entry retain their separate authority. This coordinates pre-submission editing and does not roll back frozen workloads.

Single Entry excludes staged paths/images, open pickers, active capture/registration/removal, unresolved outcomes and observed nonempty pending inventory. After reserving a capable Runner it requires a fresh successful empty inventory before PTY delivery and rechecks readiness. Legacy Runners retain the manual `/files` path with no fabricated receipts or inventory. No terminal scraping or media locator guessing is used.

Windows `desktop_terminal/clipboard.rs` owns native PNG staging inside each existing `Session`. It validates complete PNG pixels before writing, creates independent unpredictable files under a private Hub directory in the resolved Windows temporary directory, and retains creation handles with verified file identity. The native staging command requires the exact window-owned, authenticated and available Runner session. Capture is advertised when Windows Native I/O, the live session and authenticated registration are available; unsupported platforms and legacy Runners remain unavailable. Empty or unsupported clipboard contents produce an actionable per-capture error. The frontend reuses Native I/O conversion and retains the originating session across asynchronous completion and tab switches. Selection and native session budgets bound capture storage; compact process-local thumbnails are revoked on cancellation, submission, history clearing and session disposal. No additional clipboard backend or generic attachment store is created.

Staged source handles allow ordinary independent Python readers while denying new writers. Registration attempts, completed registration/removal, cancellation, rejected/failed requests, unknown outcomes, inventory changes and clearing UI history never release sources: a frozen workload may still require them. Unsubmitted sources also remain under the same conservative session boundary. After verified empty-Job termination, cleanup reopens each original file object for deletion, verifies its identity and deletes through that handle. A renamed file or replacement pathname cannot redirect deletion. Directory cleanup removes only an empty owned directory, preserving unrelated contents and other sessions. Natural root exit retains the existing PTY drain behavior. Failed termination, cleanup failure or lost ownership never triggers pathname or age-based scavenging; abrupt Hub loss can leave sources behind. Image bytes, Blob URLs and staged paths are excluded from persisted tab state and diagnostics.

Authenticated session configuration is composed on this same native transport, with an explicit feature request kind and a per-session configuration service. Its separate plan/apply, catalog, receipt, timeout and default-conversion contracts are owned by [Runner session configuration](runner_session_config.md). Existing slash settings remain the terminal fallback, and current Single Entry does not call the new configuration workflow.

## Verified generated-image previews

`desktop_terminal/generated_images.rs` owns connection-scoped discovery metadata, complete ordered retrieval and PNG verification. `control.rs` discovers the optional extension only on completed authenticated observations and correlates image operations through the existing v1 identity, increasing request sequence and private Windows pipes. Paginated discovery preserves Runner order without inventing a global sequence across App Server generations. Malformed pages, changed metadata, incorrect offsets, incomplete chunks, size limits, SHA-256 mismatch and unsupported PNGs fail before byte publication. Native catalog metadata expires with that client; no media files or durable image store are created.

The window-owned `runner_images_list` and `runner_image_read` commands retain the exact original `Session` through asynchronous work. React receives only allowlisted metadata and fully verified PNG bytes. Read/verification work does not hold the session registry or control-client mutex across retrieval; the control worker continues servicing terminal-independent control requests. Missing capability leaves legacy commands and references functional.

`runnerImages.ts`, composed by each `RunnerControl`, owns selection, discovery/read state and process-local Blob URLs. `RunnerImagePreviews.tsx` displays a compact selected image, selector, enlargement dialog and ordinary refresh beside the existing terminal. The protocol supplies no terminal presentation identity, so previews claim no inline terminal position. Discovery uses the existing observation cadence with bounded refresh intervals only in the active workspace; native reads remain sequential per image. Loading, available, empty, unsupported, unavailable and failed states are distinct. Manual refresh retrieves and verifies again; stale completions after ownership ends cannot publish a preview.

The process-wide bounded cache retains selected-image resources across tab switches and revokes URLs on selection replacement, eviction, unsupported/disconnected state or session disposal. Evicting one Runner's resource does not release another Runner's resource. Bytes, image capabilities and image metadata never enter the durable tab projection or diagnostics. Native protocol fixtures, installed-Runner transport checks and actual Tauri rendering are distinct from genuine authenticated Codex image-generation acceptance, which requires a completed native image-generation event and matching retrieval. Generic tool images, file IDs without a supported resolver, terminal text, screenshots and workspace scans cannot establish that provenance.

## Source and checks

- Frontend/session integration: `src/hub/RunnerSessions.ts`, `runnerInput.ts`, `RunnerTerminal.tsx`, `RunnerComposer.tsx`, `RunnerLocation.tsx`, `runnerControl.ts`, `referenceSelection.ts`, `RunnerControls.tsx` and `RunnerReferences.tsx`; controlled transport and actual xterm rendering checks in `tests/e2e/runners.spec.mjs`. Reference transport events and receipts in these browser tests are simulated, separately from native GUI acceptance.
- Navigation, renaming, themes and resizing: `tests/e2e/hub.spec.mjs` and `tests/e2e/starter.spec.mjs` through the installed Playwright fixture.
- Native launch, PTY, staging and job ownership: `src-tauri/src/desktop_terminal.rs` and `src-tauri/src/desktop_terminal/{pty,runner,job,process,control,control_windows,references,clipboard}.rs`; focused Rust tests in `desktop_terminal/{tests,control_tests,reference_tests,clipboard_tests,clipboard_acceptance}.rs`. `src-tauri/tests/runner_job.rs` exercises detached descendants and job cleanup. `src-tauri/tests/control_handles.rs` verifies the production handle allowlist, private authentication and EOF uncertainty against a Python protocol fixture; it is distinct from installed-Runner acceptance.
- macOS containment feasibility: `python3 tests/native/macos_containment.py temp/<unique-execution>` on a native macOS host; `.github/workflows/desktop.yml` runs it on the existing hosted ARM and Intel lanes and retains its evidence artifact. A successful fixture run can report rejected candidates; it does not enable Runner launch or establish installed-Runner/GUI acceptance.
- Generated-image rules and authenticated correlation: `src-tauri/src/desktop_terminal/{generated_images,generated_image_tests,generated_control_tests}.rs`; synthetic private-pipe pagination, ordered chunk retrieval and integrity rejection in `src-tauri/tests/control_handles.rs`. Installed image/reference compatibility uses `src-tauri/src/desktop_terminal/image_acceptance.rs`. Preview interaction, rendering, tab isolation and URL release use the simulated native boundary in `tests/e2e/runners.spec.mjs`.
- Installed Runner acceptance tests are explicitly ignored by ordinary CI and require `HUB_RUNNER_ACCEPTANCE_ROOT` on Windows. They exercise authenticated observations and image capability/empty discovery, status and model cancellation, Unicode/multiline input, resize, separate sessions and owned shutdown through the production launch. The isolated pipe fixture instead requires `HUB_CONTROL_PYTHON` pointing to a direct interpreter, avoiding a venv redirector. Fixture, installed-Runner, actual native-window, and hosted CI results are distinct evidence.
