# Runner terminal ownership

## Session lifetime and identity

`src/hub/RunnerSessions.ts` owns each Runner's terminal, PTY connection, input ordering, output parser, scrollback, draft, and observed process state. `Hub.tsx` owns selection and composes the views. A keyed `Workspace.tsx` can unmount: `RunnerTerminal.tsx` only detaches its geometry observer. Selecting the tab reattaches the same xterm element and fits that existing terminal. Inactive terminals continue parsing and acknowledging output; selection never launches or closes a process.

Names are local display labels. The row identity and its current native PTY identity remain stable when renamed. Rows retain creation order, and Single Entry remains above their independently scrolling list. Tab metadata survives reopening through the Hub-owned workspace boundary below; terminal buffers, drafts and execution attempts remain process-local.

Composer drafts and pending submission belong to the session snapshot. Switching views during configuration, work admission or a foreground PTY reply preserves its disabled/busy state and cannot submit the same draft again. A verified work start clears only the originating draft; unknown delivery retains it and prevents replay.

The connected workspace gives remaining central height to terminal output; xterm owns log scrolling, while the bottom composer has bounded independent overflow. Search text belongs to the process-local session and survives keyed view changes. Process exit retains the terminal buffer and displays the observed exit code independently of canonical work outcome. `tests/e2e/log-viewport.mjs`, registered by `runners.spec.mjs`, exercises completed output, search, wheel scrolling and tab return at short and normal desktop heights using the simulated native bridge.

## Installation startup gate

`Hub.tsx` initially composes the mandatory `AppSettings.tsx` dialog. `RunnerLocation.tsx` reads the saved installation and verifies it through `runnerInstallation.ts` and native `runner_resolve` before admitting the workspace. Empty, missing or invalid installations retain the dialog; Escape and backdrop interaction cannot dismiss required setup. Pending native verification disables path changes and exposes progress. Language and theme remain available in setup.

The native resolver accepts the Workspace or its `agent_runner` folder and verifies managed Python against the actual Runner package. Success saves the normalized location through the existing installation storage owner, selects Single Entry, and calls `RunnerSessions.setInstallation`. In normal Hub startup, that verified handoff restores saved tabs once, preserving each tab's installation and recovery context, then prepares the spare. Retaining the session owner alone does not restore or launch anything, and pre-admission notifications cannot overwrite saved tabs. Explicit session allocation retains its existing API and restores workspace metadata before appending; the required modal prevents ordinary UI allocation before verification.

The toolbar App settings dialog reuses the same verification form for later changes. Editing or rejecting a draft preserves the prior verified installation; successful changes affect new allocation and the spare, never retargeting existing tabs. Installation management is absent from central output. Directory browsing uses the existing native I/O helper only after a Tauri runtime check; browser previews receive localized desktop-launch guidance while manual typing and paste remain available. Plugin/capability failures retain their own diagnostics.

Focused browser checks live in `tests/e2e/installation-setup.mjs` and `runner-add-directory.mjs`, registered by `runners.spec.mjs`. Their simulated native bridge does not establish Windows picker acceptance. The root launcher uses its supported checkout-local `target.mjs tauri` selection; shared launcher resources and permission configuration remain independently owned.

## Hidden spare and promotion

`RunnerSpare.ts` owns one speculative session lifetime under `RunnerSessions`, reusing `RunnerSession`, `RunnerControl`, terminal parsing and the native PTY registry. It has no workspace record or assigned visible identity. Workspace restoration finishes before spare preparation can publish changes. The installation startup gate supplies verified installations; the spare does not independently restore or resolve the saved path. Each native launch also retains its installation verification and platform containment gate.

Usability requires fresh authenticated canonical observations, complete account/model/source/run-mode selection, released execution authority, no foreground/setup/confirmation/suspension or unsettled control state, available local input/configuration state, and a negotiated terminal input protocol. Spawn success and terminal text cannot establish readiness. Hidden output is parsed and acknowledged by the same terminal, including query replies and input-mode negotiation. Preparation is bounded; launch, readiness or transport failure exposes an actionable unavailable state without automatic launch retries. A failed owned cleanup blocks further prewarming for that owner.

`RunnerSessions.promoteSpare(): RunnerSession` is the assignment integration boundary. It synchronously rechecks readiness, takes the existing session and assigns its UUID, name and creation order under the workspace owner. The returned session retains its native PTY/control identity, parser, input state and scrollback; no launch occurs for promotion. It then belongs to the ordinary visible registry and persistence boundary. One replacement is prepared through the spare owner's serialized launch/cleanup operation. Rapid promotion while that replacement is unavailable throws `HubError`; Single Entry uses the supported fresh-launch path when no spare is ready. Promotion itself performs no reservation, configuration or instruction submission.

Installation changes and Hub disposal invalidate the spare generation, stop observing its terminal/control resources and join any late PTY open plus exact owned close before a replacement can start. Late launch results cannot publish another installation or revive a disposed spare. Active visible sessions remain independent. Both the sidebar add action and Single Entry use `RunnerSessions.allocate`: promote a matching verified ready spare, otherwise use the supported fresh launch. Native Windows ownership remains with the existing per-session Job Object; macOS Runner launch remains unavailable under the containment restriction below.

The green centered plus is an action at the end of the Runner list, including the empty list; it has no workspace record. Each allocation appends one real tab in creation order before that action and selects it. Manual activation is guarded against concurrent clicks until launch settles. A failed fresh launch retains its explicit failed tab and diagnostic, without automatic retry. The same list preserves rename, middle-click close and unread work indicators.

Single Entry omits the central heading, badge and decorative starting prompt. The empty sidebar retains Single Entry and the add action without explanatory empty text. Normal spare preparation/readiness stays internal; allocation errors and assignment results remain in their existing action-owned surfaces.

## Durable workspace and recovery

`RunnerWorkspace.ts` owns the versioned `agent-runner-hub.workspace.v1` local-storage record and its explicit metadata projection. `RunnerSessions.ts` restores the validated records in saved creation order before launching any processes. The manifest retains stable Hub IDs, labels, order, verified installation roots, launch intent and separate last-authenticated and historical target/run-mode/workflow contexts. A single atomic replacement commits relevant changes during use; failed writes retain the prior commit and display a warning. Unsupported or unreadable manifests remain untouched. Invalid or duplicate records are skipped independently with a visible diagnostic.

The optional `recoveryHint` retains the earlier process context while historical recovery remains unconfirmed; `lastVerified` continues following fresh authenticated observations. On load, existing version-1 records without a hint promote their saved `lastVerified` before any fresh process starts. An existing hint always survives later observations, setting changes and reopening. Both contexts use the same explicit nonsecret projection; neither provides current settings or recovery authority. Current settings come only from the current control snapshot.

Previously running or still-starting tabs invoke the existing native Runner launch path once each. Installation resolution and managed-runtime verification happen again before process creation. A missing installation or failed launch remains in its own tab for the next reopening; ended tabs remain visible without starting a process. Native PTY/control identities are newly allocated and never loaded from storage. Tab switching retains the new session mapping. Window teardown preserves the committed launch intent while the native owner settles all descendants.

`RunnerRecovery.tsx` distinguishes a restored workspace and fresh process from unconfirmed historical work. It labels the retained target, binding, run mode and workflow as previous-process information, separately from current settings, and offers `/recover` only from a fresh canonical visible/enabled command projection. Runner owns candidate discovery, selection, admission, confirmation and continuation in that tab's terminal. Rejection, pending interaction, unavailable recovery and command completion remain distinct; accepting a command alone does not establish successful TaskRun, DirectRun or IssueRun recovery or retire the historical hint.

The recovery projection supplies no authoritative historical work-recovery receipt. Current authenticated work identities remain live only; Hub never persists them or private transport identity. The manifest excludes PIDs, handles, control keys/capabilities, credentials, terminal output, composer input, submissions, completion/unread state and uncertain commands. Restoration never reconnects to old processes, fabricates historical completion or replays instructions, selections or commands. Scheduling and automatic work recovery remain outside this integration.

## Single Entry assignment

`DirectoryInput.tsx` shares native `selectFolder` browsing between installation and Hub Direct Root fields. Typing, paste and browsing edit only the requested value. Cancel leaves it unchanged; owner/draft guards discard late picker results after edits, view changes or session end. Installation verification remains explicit; configuration is authorized only by instruction submission. Hub selections retain their existing safe preference projection.

Single Entry owns the source draft, requested defaults, allocation policy and allocation/start summary. Each owning session composes `RunnerWork` through `RunnerControl`; work observations, native receipts, original submission correlation and uncertainty stay there. Preferences retain only the safe selections described in [Hub preferences](hub_preferences.md), never an assignment, instruction or work identity.

Allocation defaults to always-new. The explicit reuse-idle toggle considers visible sessions in creation order, refreshes canonical work/idle evidence and reserves the exact eligible session before configuration. Reserved sessions cannot compete for another assignment. New allocation promotes a ready hidden spare without changing its terminal, process or control identity; otherwise it uses the existing supported fresh launch. `RunnerSpare` alone replenishes a consumed spare. Single Entry immediately selects the allocated tab. Loss of prerequisites after selection leaves that assignment held without silently selecting another Runner.

Eligibility requires negotiated input, untouched manual input, an empty Hub composer, released canonical execution/workflow authority, no foreground/setup/confirmation/suspension or unsettled control/configuration/work evidence, and enabled `/target` and `/files`. Attachment preflight excludes prepared or uncertain references and verifies empty inventory. Final readiness, reservation and inventory are checked again before ordinary work submission.

`runnerSubmission.ts` owns the shared ordered configuration/work pipeline for Single Entry and Runner-tab submission. Each uses the destination's complete authenticated catalog to resolve Target, exact account identity, model/reasoning/tier, Run Mode and explicit Direct Root. It inspects, resolves and plans, applies only necessary changes through `RunnerConfigService`, verifies current state, then runs entry-specific admission before one `work.submit`. No-op plans are verified without Apply. Missing Root, unsupported or legacy identities, rejected/confirmation-required plans, partial application and unknown effects leave work unsent. Confirmed per-setting receipts remain available in the read-only configuration evidence panel.

Single Entry retains allocation and reservation. A Runner composer snapshots only that tab's HubSelections and never allocates another Runner. Its final admission checks fresh released authority and the existing attachment preflight. The verified attachment lease authorizes only its exact work submission; status reads remain available to reconcile uncertain delivery while that lease is retained. Tab changes cannot retarget requests. Rejected work retains the draft; unknown delivery retains the original attempt and reference ownership until authoritative rejection or start, with no automatic replay.

Ordinary instructions use one authenticated `work.submit`. Read-only `work.status` always names that original request ID in the same native session/generation. Queued is transport admission only; `dispatch_received` completes the submission RPC with admission still pending. Neither establishes work admission or start. Only Runner's `event_id` and permanent `started_event_id` supply start evidence. A verified start releases assignment ownership and clears the source draft; a late matching receipt can establish that boundary. Definite rejection preserves an unsent draft for explicit release or transfer. Without verified start evidence, ambiguous submission, lost status or session exit retains assignment ownership and blocks replay. Unknown completion does not erase an already verified start or make that Runner reusable.

Runner work states preserve admission, active execution, suspension, incomplete work, rejection and unknown outcomes independently from `terminal` and `outcome`. A Task or Issue is complete only when its whole-work owner establishes that terminal outcome; an Agent Turn result cannot substitute. The Runner tab offers read-only status refresh and keeps its original full terminal output. Single Entry contains allocation and verified start evidence only; terminal text never establishes work facts.

Explicitly typed slash commands retain one PTY submission. Authenticated foreground-interaction evidence routes composer replies to that same PTY without configuration, reference preflight or new work. Successful PTY delivery does not establish work acceptance. Assignments and instruction delivery are never restored or automatically replayed.

## Tab status and closing

`RunnerWork` is the live per-session owner of both API and terminal work, including activity, terminal outcomes and unread decisions. After authenticated readiness, work v1 discovery starts at `work.list` cursor zero and follows the returned session watermark through bounded pages. It upserts newer evidence by authenticated session/generation and stable observation identity; repeated pages and updates do not create work or repeat a notification. API observations merge into their original submission attempt, preserving its delivery receipt and uncertainty. Terminal observations require authenticated Runner evidence with a null submission request ID; PTY bytes and local input never establish an observation.

Read-only work requests never overlap. Discovery yields to foreground configuration/control/attachment and image operations; a pending discovery read does not disable those operations or PTY input. `work.observe` rereads a returned individual identity without creating another state owner. Discovery continues after a work terminal so that short sequential work remains discoverable, and stops with the owning session. Malformed or incomplete pages preserve the cursor; a cursor-ahead or unsupported-operation rejection stops discovery without inventing a result. Older Runners retain original-request API status tracking and supply no inferred PTY completion.

Whole-work terminal outcomes distinguish completion, failure and interruption; suspension and incomplete work need attention, including terminal partial IssueRun outcomes. Unknown evidence stays unknown. Direct-family success requires settled Turn evidence; Task and Issue work require their whole-work final owners. Agent messages, terminal output, transport admission and intermediate Task/Issue stages never establish completion.

The owning work service retains unread terminal outcomes in live memory independently of mounted views, including while later work starts. `RunnerSessions` projects that status onto the existing `Sidebar` indicators; `Hub` acknowledges it only after the owning tab is viewed. Selecting another tab, repeated observations, renaming and language/theme rerenders preserve that acknowledgment boundary. Fresh canonical execution/attention observations cover sessions with no known work without inventing a completion history. Work observations and notification state never enter durable workspace storage.

The sidebar trash icon immediately follows rename; both appear on hover and keyboard focus. Trash and middle-click use the same removal path without selecting or renaming the row. `RunnerTabRemoval` asks one consequential confirmation when the Hub preference is enabled. The Runner workspace has no redundant title, badge or close/terminate header.

`RunnerSessions.close` synchronously commits the remaining workspace records and retires the visible session before awaiting native operations. A persistence failure retains the original live row, terminal and diagnostic. Selected removal chooses the next creation-order tab, then the previous tab, then Single Entry; background removal preserves selection. Removed tab preferences are forgotten independently; preference write failures remain visible.

The same session owner keeps removed sessions in mutually exclusive checking, hidden idle, terminating or failed states. Reuse requires freshly verified released idle authority, empty reference inventory, settled work/configuration/control state, no reservation, input, draft or attachment uncertainty, and negotiated input capability. Unverified or unsafe sessions terminate through their exact existing PTY owner. Hidden eligibility is monitored, and allocation synchronously claims a matching idle session before reservation callbacks. Promotion creates a new UUID, creation order and Hub selection owner, clearing old recovery/search/log presentation without launching another process or exposing hidden history.

Close acknowledgment alone is insufficient: successful native exit settlement must arrive. Failed or unconfirmed termination retains the original terminal and error in a conditional sidebar section; selecting it reattaches full existing scrollback without launching or restoring a durable tab. Later verified settlement retires internal resources. Stale callbacks cannot restore deleted records or allocate a session twice. Visible, hidden and failed sessions remain under exact owned shutdown cleanup; neighboring Runners and RunnerSpare stay independent.

## Native launch and shutdown

`src-tauri/src/desktop_terminal/runner.rs` accepts an installed workspace or its `agent_runner` folder. It verifies that the managed Python environment imports that installation's exact Runner source. Windows launch resolves the underlying interpreter and supplies the managed venv launcher context, avoiding an extra venv redirector PID while retaining the same environment. It runs the public `-I -m runner run --repo-root <workspace>` entry with the retained backend. Shell aliases are not executables. Invocation-scoped Runner coordination variables and Python path overrides are removed from the launch environment. Runner source, environments, credentials and runtime data stay in the configured installation.

On Windows, verification still uses the canonical filesystem identity, while returned DOS/UNC installation paths use ordinary external argument spelling. This prevents verbatim canonicalization prefixes from creating a mismatch with paths reported by Runner's App Server. Other device path kinds retain their original spelling.

The existing Desktop Terminal bridge and native `Sessions` registry remain the PTY backend. Windows Runner sessions use a separate non-inheritable Job Object with kill-on-close and no breakaway permission. The vendored portable-pty extension composes JOB_LIST, HANDLE_LIST and ConPTY startup attributes. Assignment occurs before Python executes; assigning an already running child would leave a descendant-creation race. Only the two dedicated child control endpoints are inherited. Parent endpoints and the Job Object remain non-inheritable; redundant child endpoints close immediately after creation. The Hub remains outside those per-Runner jobs.

Explicit termination, natural root exit, native window destruction, and final native ownership cleanup settle the owned job. Job termination waits for its active process count to reach zero. Natural exit is published after residual descendant cleanup and terminal output drainage. Unrelated PTY sessions and unrelated processes are outside that job. The generic Desktop Terminal request retains its original direct-child behavior.

macOS installation resolution is implemented, but Runner launch is gated before Runner process creation: initial POSIX process groups cannot contain children that start another session. Per-user launchd service removal does not establish detached-descendant ownership. Darwin's recursive kqueue tracking flags are unsupported; per-process exit observation does not create inherited membership. No supported containment mechanism is selected for production. Installed-Runner and native-window acceptance remain separate from compilation and process-fixture evidence.

The vendored Unix cloned killer sends SIGHUP to the direct child PID. Neither this operation nor killing the initial process group establishes detached-descendant containment. The existing Runner's POSIX group cleanup and cooperative shutdown are insufficient evidence to remove the macOS launch gate; a matching native detached-descendant fixture and installed-Runner acceptance remain required. A launchd job's process-group cleanup must not be treated as equivalent to a Windows Job Object.

`tests/native/macos_containment.py` executes bounded native fork/session and launchd experiments through the existing desktop CI on both macOS architectures. `macos_kqueue_probe.c` separately compiles and executes API registration receipts and fork-event observations. The fixture uses a private Unix-socket roster and per-process exit events as independent ground truth; candidates receive only their original PGID or unique service target. This cooperative roster is a fixture oracle, never a proposed production ownership mechanism.

Every fixture participant has an independent absolute wall-clock expiry, including orphans and processes that ignore termination signals or close standard streams. Calibration omits candidate cleanup and observes that expiry. Separate control channels clean up failed candidates, and only exact ephemeral launchd services are removed. CI retains host/manual details, operation results, per-process observations and final absence evidence even on failure. It does not copy or require a private Runner installation.

## Native executable build entry

`tools/hub-native.mjs` composes the installed Tauri host preparation, checkout build lease, backend staging and desktop feature selection. Its explicit absolute Cargo target directory allows Windows callers to select a short real output/cache path while frontend and backend staging remain checkout-local. It does not change managed build tooling, Runner installations, original Cargo locks or previous frontend output. `--help` describes build and native test commands; Cargo owns the selected output cache.

The standalone build passes a relative frontend directory to Tauri so Windows drive letters cannot be interpreted as URL schemes. The ordinary Tauri CLI enables production asset serving even for this debug executable; no test runtime branch or additional Cargo feature is used. The standalone build is distinct from Build System packaging and native development. A successful build establishes compilation and executable availability; GUI interaction, process cleanup and installer acceptance require their own observations. Build System remains the packaged-product owner.

## Input and process observations

`runnerInput.ts` honors Win32 input mode through ConPTY. Foreground replies and typed slash commands encode Unicode as UTF-16 key records and embedded line breaks as Shift+Enter, followed by Enter; VT uses negotiated bracketed paste. Ordinary instructions use the authenticated work API, not this editor. xterm is read-only during ordinary composition, retaining output parsing, query replies, search, selection and scrollback. Fresh authenticated foreground or pending-interaction evidence enables necessary terminal keys and cursor feedback.

The native feature surface implements session configuration and work, with configuration explicitly declaring `interaction_owner: runner_terminal`. It has no typed foreground-answer operation or terminal-editor suppression mode. Runner-owned selection/detail/cancellation prompts therefore retain terminal interaction; Hub neither synthesizes private confirmations nor filters PTY output to conceal the retained editor. GUI composer replies support line answers, while prompts needing navigation or keys use the foreground-only terminal. This is an API limitation, not evidence of a complete GUI replacement for every confirmation.

The UI reports starting, successful process launch, launch failure, and observed exit/code or transport errors. Terminal text never establishes task readiness, work completion, or assignment state. Launch and unexpected-exit failures affect only that session. Single Entry assignment uses the authenticated evidence above; workspace restoration never restores its pending assignments. xterm query replies and focus notifications retain their protocol path without becoming user-draft evidence; ordinary terminal typing still excludes automatic assignment.

## Local control and reference boundaries

`desktop_terminal/control.rs` owns the native v1 protocol and allowlisted public snapshots; `control_windows.rs` owns anonymous pipes, secure random launch identity/key, bounded I/O and worker cleanup. The hello must match the created child PID and expected fresh session, and an authenticated observation must complete before commands become available. Keys and raw wire identities remain native-only. Each existing session owns one client until exact process exit, termination or Hub closure, independent of selected tabs.

Controlled Windows launches use explicit NULL standard-handle slots with `STARTF_USESTDHANDLES`, allowing ConPTY to initialize console streams while excluding Hub stdio from inheritance. The compatible installed Runner public entry acquires its implementation generation and retains interactive ownership in the exact created process for controlled launches. Ordinary launches retain Runner's restart supervisor; controlled launches canonically disable `/restart`. Hub uses the public entry without bypassing generation ownership, weakening PID verification or replaying uncertain commands.

Runner owns canonical settings, command availability and foreground coordination. Native observations refresh those projections without parsing terminal text. Queued admission, pending terminal interaction, accepted/rejected completion, failure and uncertain outcomes remain separate. Only completed responses can supply owner status and allowlisted change acknowledgements; a completed command's canonical observation updates the existing snapshot immediately. Terminal cancellation retains Runner's rejected/CANCELLED outcome. The PTY exit event includes the final allowlisted native snapshot so a completed result is not lost between frontend polls. Disconnects preserve uncertainty for requests without authoritative completion; commands are never replayed automatically. A pending foreground interaction does not time out while awaiting terminal answers.

`runnerControl.ts` owns the frontend snapshot reader and canonical command dispatch. The right task panel retains Hub selection fields and read-only configuration evidence, without command shortcut lists, slash buttons or manual Plan/Apply actions. Recovery retains its authenticated action with a human-readable status label. The connected workspace keeps terminal scrolling inside xterm and bounded composer scrolling at the bottom.

`referenceSelection.ts` owns independent, process-local selections for Single Entry and every Runner composer, together with destination-bound registration/removal receipts. `ComposerAttachments.tsx` presents removable path chips, pasted-image previews, ordering controls and attachment-local reconciliation. Pickers and composer-position native drops stage paths without reference requests; native hover highlights the composer. DOM drops cannot supply native paths. Ctrl+V consumes image bytes from the paste event while ordinary text paste remains browser-owned. Unsupported image formats produce a visible failure; no submission reads the live clipboard. Neither selections nor image bytes enter configuration preferences or durable tab state.

`desktop_terminal/references.rs` validates the allowlisted reference extension and metadata. Capability discovery uses only a completed authenticated observation; the exact v1 hello remains unchanged. Registration shares the existing pipe, private identity and monotonically increasing request sequence with observe/command. Only completed `registration_status: registered` with a valid stable reference ID becomes registered. Native admission failure, queued admission, foreground interaction, rejection, failure and unknown outcome remain distinct. Image-detail selection and cancellation use the existing Runner terminal. Unknown attempts are retained and never automatically repeated or matched by name, path or terminal text.

Inventory reconciliation reads all `references.list` pages twice and requires matching complete ordered samples, consistent totals, advancing offsets and unique stable IDs. Changing, incomplete or oversized samples block submission. These are conservative samples, not a transactional Runner snapshot. Display indexes and names never identify a removal. The optional authenticated `reference_removal` capability enables `references.remove` by the exact committed ID; only its completed matching receipt confirms removal. Pending or unknown removal blocks ordinary submission until the owning Runner authoritatively confirms absence. Missing removal support remains explicit and unresolved beside the affected attachment. No receipt or inventory sample releases source bytes.

Both composers freeze their draft and attachment selection before configuration and compose attachment preflight through the shared `submitConfiguredWork` path. Single Entry binds its selection only to the allocated session after verifying empty destination inventory; each Runner tab uses its exact session. Preflight stages frozen PNG sources, serializes surviving registrations, waits for completed receipts, and verifies intended IDs and cancelled-ID absence against the stable final pending set. Other pending references require explicit review. Only verified reference preparation permits one authenticated work submission. Verified work start clears only the originating draft and selection. Rejection or definite failure retains selected items and known partial registrations for exact-ID reconciliation; uncertain attachment/work attempts retain their original session and block unsafe replay. Runner-owned image-detail/cancellation prompts and terminal replies remain interactive.

Single Entry excludes destinations with tab-owned staged paths/images, open pickers, active capture/registration/removal, unresolved outcomes or nonempty pending inventory. Its own selections remain intact before allocation. An unsent assignment cannot be released to another destination while its attachments retain active reference attempts. Ordinary Single Entry work requires work/configuration capabilities; attachment submission additionally requires the supported reference API. No terminal scraping or media locator guessing is used.

Windows `desktop_terminal/clipboard.rs` owns native PNG staging inside each existing `Session`. It validates complete PNG pixels before writing, creates independent unpredictable files under a private Hub directory in the resolved Windows temporary directory, and retains creation handles with verified file identity. `runnerControl.stageImage` sends the paste-event Blob bytes through the existing `runner_stage_clipboard` command only after destination configuration. The command requires the exact window-owned, authenticated and available Runner session. Unsupported platforms/builds and unavailable staging retain the selection and prevent work submission. Process-local previews are revoked on cancellation, verified start and disposal. Native session budgets and cleanup ownership remain unchanged. Browser paste/drop simulations do not establish actual Windows WebView acceptance; a host that supplies no image in its paste event has no frozen-image capture path and must use the visible file picker.

Staged source handles allow ordinary independent Python readers while denying new writers. Registration attempts, completed registration/removal, cancellation, rejected/failed requests, unknown outcomes, inventory changes and clearing UI history never release sources: a frozen workload may still require them. Unsubmitted sources also remain under the same conservative session boundary. After verified empty-Job termination, cleanup reopens each original file object for deletion, verifies its identity and deletes through that handle. A renamed file or replacement pathname cannot redirect deletion. Directory cleanup removes only an empty owned directory, preserving unrelated contents and other sessions. Natural root exit retains the existing PTY drain behavior. Failed termination, cleanup failure or lost ownership never triggers pathname or age-based scavenging; abrupt Hub loss can leave sources behind. Image bytes, Blob URLs and staged paths are excluded from persisted tab state and diagnostics.

Authenticated session configuration is composed on this same native transport, with an explicit feature request kind and a per-session configuration service. Its separate plan/apply, catalog, receipt, timeout and default-conversion contracts are owned by [Runner session configuration](runner_session_config.md). Single Entry reuses that service before work submission; existing slash settings remain the terminal fallback.

## Verified generated-image previews

`desktop_terminal/generated_images.rs` owns connection-scoped discovery metadata, complete ordered retrieval and PNG verification. `control.rs` discovers the optional extension only on completed authenticated observations and correlates image operations through the existing v1 identity, increasing request sequence and private Windows pipes. Paginated discovery preserves Runner order without inventing a global sequence across App Server generations. Malformed pages, changed metadata, incorrect offsets, incomplete chunks, size limits, SHA-256 mismatch and unsupported PNGs fail before byte publication. Native catalog metadata expires with that client; no media files or durable image store are created.

The window-owned `runner_images_list` and `runner_image_read` commands retain the exact original `Session` through asynchronous work. React receives only allowlisted metadata and fully verified PNG bytes. Read/verification work does not hold the session registry or control-client mutex across retrieval; the control worker continues servicing terminal-independent control requests. Missing capability leaves legacy commands and references functional.

`runnerImages.ts`, composed by each `RunnerControl`, owns selection, discovery/read state and process-local Blob URLs. `RunnerImagePreviews.tsx` retains the selected image, selector, enlargement dialog and ordinary refresh in a collapsed-by-default disclosure beside the terminal. The protocol supplies no terminal presentation identity, so previews claim no inline terminal position. Discovery uses the existing observation cadence with bounded refresh intervals only in the active workspace; native reads remain sequential per image. Loading, available, empty, unsupported, unavailable and failed states are distinct. Manual refresh retrieves and verifies again; stale completions after ownership ends cannot publish a preview.

The process-wide bounded cache retains selected-image resources across tab switches and revokes URLs on selection replacement, eviction, unsupported/disconnected state or session disposal. Evicting one Runner's resource does not release another Runner's resource. Bytes, image capabilities and image metadata never enter the durable tab projection or diagnostics. Native protocol fixtures, installed-Runner transport checks and actual Tauri rendering are distinct from genuine authenticated Codex image-generation acceptance, which requires a completed native image-generation event and matching retrieval. Generic tool images, file IDs without a supported resolver, terminal text, screenshots and workspace scans cannot establish that provenance.

- Native launch, PTY, staging and job ownership: `src-tauri/src/desktop_terminal.rs` and `src-tauri/src/desktop_terminal/{pty,runner,job,process,control,control_windows,references,clipboard}.rs`; focused Rust tests in `desktop_terminal/{tests,control_tests,reference_tests,clipboard_tests,clipboard_acceptance}.rs`. `src-tauri/tests/runner_job.rs` exercises detached descendants and job cleanup. `src-tauri/tests/control_handles.rs` verifies the production handle allowlist, private authentication and EOF uncertainty against a Python protocol fixture; it is distinct from installed-Runner acceptance.
- macOS containment feasibility: `python3 tests/native/macos_containment.py temp/<unique-execution>` on a native macOS host; `.github/workflows/desktop.yml` runs it on the existing hosted ARM and Intel lanes and retains its evidence artifact. A successful fixture run can report rejected candidates; it does not enable Runner launch or establish installed-Runner/GUI acceptance.
- Generated-image rules and authenticated correlation: `src-tauri/src/desktop_terminal/{generated_images,generated_image_tests,generated_control_tests}.rs`; synthetic private-pipe pagination, ordered chunk retrieval and integrity rejection in `src-tauri/tests/control_handles.rs`. Installed image/reference compatibility uses `src-tauri/src/desktop_terminal/image_acceptance.rs`. Preview interaction, rendering, tab isolation and URL release use the simulated native boundary in `tests/e2e/runners.spec.mjs`.
- Installed Runner acceptance tests are explicitly ignored by ordinary CI and require `HUB_RUNNER_ACCEPTANCE_ROOT` on Windows. They exercise authenticated observations and image capability/empty discovery, status and model cancellation, Unicode/multiline input, resize, separate sessions and owned shutdown through the production launch. The isolated pipe fixture instead requires `HUB_CONTROL_PYTHON` pointing to a direct interpreter, avoiding a venv redirector. Fixture, installed-Runner, actual native-window, and hosted CI results are distinct evidence.
