# Hub event history

## Lifetime and ownership

`Hub.tsx` composes `HubLog` and its `HubLogCapture` adapter independently of the keyed Workspace. New records use stable `system`, `task` and `settings` components; outcomes remain in actual/code fields. View detachment affects presentation only. The recorder neither launches processes nor sends or retries Runner instructions. `HubPreferences` owns retention selection; workspace restoration and Runner buffers remain separate owners.

The projection retains component/operation, relevant Runner and Target, expected/actual state, safe code and next action. Raw exceptions and interpolated user content, instruction bodies, credentials and media are excluded. Structured message identities remain visible when arbitrary details cannot safely be retained.

System capture uses visible session lifetime states and meaningful control connection changes. `RunnerSessions.subscribeLifecycle` forwards confirmed restart/shutdown and hidden-spare evidence without retaining another history. `RunnerSpare` emits preparation once per slot after authenticated canonical readiness and input availability, independently of later readiness refreshes or temporary assignment locks. Promotion records the assigned visible Runner name; replacement preparation is a separate event. Startup and replacement failures use the lifecycle owner's failure path, never a busy snapshot.

Task capture uses all retained `RunnerWork.attempts`, confirmed admission/start evidence and original `WorkObservation` terminal outcomes, preserving rejected, interrupted, incomplete and unknown states. Submission rejection or uncertain delivery without an observation remains separate evidence. Settings capture uses explicit `RunnerConfigService.applications` receipts and validated apply results, including partial, failed and unresolved outcomes. Inspection, catalog acquisition, planning, work-list requests, ordinary polls and assignment progress messages produce no entries. In-memory suppression distinguishes session instances, attempts and outcomes; it is neither a persisted ledger nor replay of historical events.

## Durable order and failure boundary

`src-tauri/src/hub_log.rs` owns the main-window-only `hub_log` command and app-local `hub-logs/events.jsonl`. Its process-wide serialized native operation restores records before append or age pruning, assigns ordered identity and timestamp, and syncs append bytes. The frontend queue restores before submitting queued startup events. Original stored fields pass through one formatter for live and restored display; restoration never replays Runner effects.

Valid retained history is independent of the renderer's progressively expanded window. Pruning uses the persisted preference, keeps records at the cutoff, and stages replacements only inside owned log storage. Idle cleanup runs through the same owner. Missing preferences select thirty days; [Hub preferences](hub_preferences.md#independent-preference-storage) owns input validation and saved-value protection.

Malformed history is preserved byte-for-byte, with valid lines exposed and further writes stopped. Read, write and prune failures expose stable storage codes. The frontend retains previously loaded history and explicitly marks pending records as unconfirmed; memory display does not prove a save, and uncertain writes are not automatically replayed. A repaired storage location is reloaded on the next application start. The logger cannot guarantee survival of records whose native save failed.

## Presentation and evidence

`HubLogView.tsx` uses the central Single Entry output area and existing terminal/theme vocabulary. Read-only rows align local `YYYY-MM-DD HH:mm:ss` timestamps, neutral localized System/Task/Settings categories and wrapping event messages. `HubLog.ts` projects known operations and confirmed structured outcomes without displaying raw diagnostics. Success is green, uncertainty/warnings yellow and verified failures red. Legacy records retain safe context and an explicit unverified historical label; presentation never rewrites their persisted fields.

Initial display and Single Entry re-entry start at the newest retained record. Appends follow only while the view is at the bottom. Scrolling upward suspends following; returning to the bottom resumes it. The initial recent-record window pins its first sequence so appends cannot evict viewed rows. Older-record expansion restores the visible row anchor instead of following the newest record. These are transient view concerns; capture, retention and pending-save/storage-error indications remain independent.

Representative evidence: `tests/e2e/hub-log.spec.mjs` covers queue ordering, capture lifetime, deduplication/privacy, preference migration and view/settings behavior; `tests/e2e/hub-log-presentation.spec.mjs` exercises localization, timestamps, outcome styling, narrow wrapping and history anchors across expansion/appends. `src-tauri/src/hub_log/tests.rs` exercises actual disk round trips, controlled-time expiration and parse/I/O preservation. `tests/native/webdriver/hub-log.mjs`, selected through `tools/native-probe/hub.mjs`, exercises an actual Candidate Hub and Runner tab, structured rows, app-local disk and a fresh native process using the same isolated data. Native platform claims require that case's recorded result; browser transport simulations alone do not establish native survival.
